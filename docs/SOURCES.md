# Источники вендора

Карта того, откуда берётся каждый заимствованный компонент, с контрольными
суммами и способом промера. Назначение одно: собрать репозиторий с чужой
машины. `vendor/` в git не входит (`.gitignore:4`, 67,65 МБ), поэтому без
этой карты сборка невозможна в принципе — а с ней каждый архив проверяется
до начала компиляции.

Всё ниже промерено 2026-10-27 на машине из
[`ENVIRONMENT.md`](ENVIRONMENT.md). Метод промера указан для каждой строки,
потому что «проверено» без метода — это мнение, а не факт.

## Как читать эту карту

| колонка | что значит |
|---|---|
| версия | та, которой дерево объявляет **само себя** (`configure.ac`/`AC_INIT`, `pkgIndex.tcl`, `VERSION`), а не та, что в имени каталога |
| SHA-256 | дигест **нашего** файла в `vendor/`; сверяется до распаковки |
| метод получения | `GET` — обычный HTTP-запрос; `codeload` — архив git-референса; `бандл` — внутри чужого тарбола |
| закрепление | неподвижный релиз / тег / **подвижная ветка** — последнее опаснее, см. ниже |

Проверка одной строки:

```
curl -sS -L --fail -o vendor/<имя> '<URL>'
sha256sum vendor/<имя>          # должен совпасть с таблицей
tar -tzf vendor/<имя> | head    # или zip -l: артефакт должен читаться как архив
```

Третий шаг не украшение. `https://www.dyncall.org/pub/dyncall-0.9.tar.gz`
отвечает **HTTP 200** с `Content-Type: text/html` и `Content-Length: 0` —
то есть «успешная» загрузка пустой HTML-страницы. Сверка по одному только
коду ответа такой артефакт пропустит; сверка по дигесту поймает размер, но
не назовёт причину.

### iwidgets: почему Debian, а не апстрим (решение A7)

Берём `iwidgets4_4.1.1.orig.tar.gz` — это **orig**, то есть апстрим-исходники
без `debian/`-диффа. Проверяется третьей стороной, а не нашим словом:
собственный `.dsc` пакета (`iwidgets4_4.1.1-5`, maintainer *Debian Tcl/Tk
Packagers*, uploader Sergei Golovan, формат `3.0 (quilt)`,
Standards-Version 4.7.4) содержит блок `Checksums-Sha256`, где наш дигест
стоит рядом с ровно тем же размером:

```
572fd8eed70786b1fbff6e7fec62eab7bd731beea074022d1b5a480ecf2df586 720630 iwidgets4_4.1.1.orig.tar.gz
be0566c1bea9ac957b7525f8235e41c8ff8f783e252fc892c021a5880c9d71c4  6596 iwidgets4_4.1.1-5.debian.tar.xz
5bf69653956c59081bdd4d6d49e90128ea666e0145418f71156bb76dfbc99cdb  2039 iwidgets4_4.1.1-5.dsc
```

Из этого следует важная для лицензий вещь: раз мы берём `.orig`, а не
`.debian.tar.xz`, **дебиановские quilt-патчи к нам не попадают**. Значит
расхождение нашего дерева с апстримом объясняется целиком нашими правками
`patches/iwidgets/` (13 файлов, индекс в [`../patches/README.md`](../patches/README.md)),
и приписывать их Debian было бы неправдой.

### treectrl: имя каталога врёт, версия в дереве — 2.5.2

Расхождение, которое раньше жило в документации как «2.5.1 в скриптах,

(`vendor/tktreectrl-2.5.1.tar.gz`) и каталога; фактически это 2.5.2.
Числа «2.5.1» в сборочных скриптах и тестах — имя пути, а не версия
компонента.

### mpexpr и itk: это зеркала, а не канон

Канон обоих живёт в fossil (`core.tcl-lang.org/mpexpr` и
`core.tcl-lang.org/itcl`), а наши артефакты байт-в-байт равны архивам
GitHub-зеркал: `tcl-mirror/mpexpr` («git mirror of
http://core.tcl.tk/mpexpr», верхний каталог `mpexpr-master/`) и `tcltk/itk`
(официальное зеркало проекта, «Mirror of core.tcl-lang.org», верхний
каталог `itk-main/`). Fossil как канал не годится: `core.tcl-lang.org`
троттлит примерно 20-24 КБ/с со сбросом соединения, и за 3000 секунд ожидания
fossil-тарбол Tcl не отдал даже себя целиком.

mpexpr: официальный релиз `mpexpr-1.2.tar.gz`
(`downloads.sourceforge.net/mpexpr/`, 365 192 B, `bc3e6b07…`) существует, но
это **другой артефакт**: пре-TEA, 50 файлов против 56, без
`win/{rules.vc,rules-ext.vc,targets.vc,nmakehlp.c}`, зато с
`win/{install.tcl,pkgIndex.tcl}`. Наше дерево — fossil master **после**
релиза 1.2 с TEA-конверсией, хотя `MPEXPR_VERSION` всё ещё `"1.2"`.
Старые попытки загрузки (архив magicsplat, 389 416 B, `5ff6eb1c…`) с нашим
артефактом **не совпадают** — использовать их нельзя.

itk: fossil-тарболы не совпадают по размеру ни один
(`itk-main.tar.gz` — 518 013 B, `itk-4-2-7.tar.gz` — 518 077 B против наших
178 751 B), и это не дыра в происхождении, а свойство экспорта fossil: он
иначе включает игнорируемые и бинарные файлы. Подтверждённый URL — зеркало
`tcltk/itk`, пин `e697407849b01d3498b56fc46e5a423690190954`.

### manifest.uuid: что он на самом деле означает

В стейдже itk лежит `manifest.uuid` =
`git-20c39a8de1bf9607c7d879d0e6d17f2ba35351c8`. Цитировать его как
провенанс-пин **нельзя**: такого объекта нет ни в `tcltk/itk`, ни в
`core.tcl-lang.org/itcl` (проверено через GitHub API — HTTP 422), и в
апстримном архиве файла `manifest.uuid` нет вообще. Его генерирует наша же
сборка: апстримное правило `$(ROOT)\manifest.uuid` (видимо как удалённые строки
хунка `@@ -135,12 +135,18 @@` в `patches/itk/win/makefile.vc.patch`) делает
`copy gitmanifest.in manifest.uuid` и `git rev-parse HEAD >>manifest.uuid`.
То есть это **наш** коммит, а не ревизия itk. Настоящий пин — `e6974078…`.

Тот же механизм у rl_json, и там он хуже: `generic/rl_jsonUuid.h`
складывается в дерево вручную (`scripts/build-msvc-ext2.bat` L14-40; индекс —
[`patches/README.md`](../patches/README.md), раздел «UUID вендора»), поэтому он
**заморожен** и не изменится, с какого бы коммита мы ни собирали. Замер 2026-10-27:
обе цепочки несут `git-20c39a8d…`, то есть коммит, который был HEAD на
момент той сборки, — и это утверждение будет ложным с каждым следующим
коммитом. У Tcl, Tk, itcl, thread, sqlite, tdbc и Img те же файлы содержат
**апстримные** fossil-ревизии (`ee6cca96…`, `988` у Img), потому что они
приходят внутри тарбола и наша сборка их не трогает.

Строка попадает в объектные файлы (`itkBase.c`, `rl_jsonBuildInfo.c`:
`PACKAGE_VERSION "+" STRINGIFY(<PKG>_VERSION_UUID)`) и лежит в отгружаемых
exe. В `package present` она не видна (замер: `itk present: 4.2.7`,
`rl_json present: 0.17.8` на всех четырёх assembly), но извлекается из
бинарника. Отдельный дефект согласованности: msvc-itk несёт
`git-20c39a8d…`, а mingw-itk — `git-` (пусто), то две цепочки одного
«того же кита» расходятся в поле, которое должно идентифицировать вендор.

## Подвижные git-референсы: почему пинить коммитом обязательно

Четыре артефакта (treectrl, mpexpr, itk, TclReadLine) получены из **ветки**, а
не из тега. Ветка может двинуться, и тогда карточка перестанет описывать то,
что мы отгрузили. Проверено отдельно: обе формы скачаны, содержимое разложено
и сравнено по относительным путям и дигесту каждого файла (для itk — 70/70
файлов совпали, см. ниже).

| компонент | наш vendor/ | ветка, скачано сейчас | коммит (пин) | файлы | расхождение содержимого |
|---|---|---|---|---|---|
| treectrl | `fe7a7a28…` 998 346 B | `fe7a7a28…` 998 346 B | `51498c7837193d621069d1159577392f2bfc1fb2` → `da93cc42…` 999 449 B | 149 / 149 | 0 |
| mpexpr | `b02c5401…` 389 336 B | `b02c5401…` 389 336 B | `1d2bf28d360da53b820ee3c5ad10e848d1af8b50` → `9c49c92a…` 389 516 B | 56 / 56 | 0 |
| itk | `54bd2e71…` 178 751 B | `54bd2e71…` 178 751 B | `e697407849b01d3498b56fc46e5a423690190954` → `d4db12ef…` 178 944 B | 70 / 70 | 0 |
| TclReadLine | `11da53cb…` 12 284 B | `11da53cb…` 12 284 B | `8cad690349a3a6b418290bbdca111383519ba02e` → `ffd7cd6a…` 12 624 B | 4 / 4 | 0 |

Три вывода, каждый промерен, а не предполагался:

1. **Наши файлы — это ровно текущее состояние веток** (дигесты совпали).
   То есть карта не устарела на момент промера.
2. **Закрепление коммитом даёт то же содержимое** — ни одного лишнего,
   недостающего или изменённого файла во всех четырёх случаях.
3. **Но байты другие**, и вот это ловушка: GitHub именует верхний каталог по
   референсу (`tktreectrl-main/` против
   `tktreectrl-51498c7837193d621069d1159577392f2bfc1fb2/`), а длина имени
   входит в каждый путь, поэтому дигест архива меняется **без всякого
   изменения содержимого** (+1103 B, +180 B, +193 B, +340 B).

Практический смысл: если скрипт загрузки будет сверять дигест веточной
формы, а качать коммитную — он откажет на корректных данных. Поэтому
единственный источник истины — **дигест той формы, которую скачиваешь**, и
переход на коммитную форму означает перегенерацию дигестов в этой карте, а
не «ошибку загрузки». Формы, которые надо пинить:


## Раскладка: архив → дерево

Ни один сборочный скрипт `vendor/` не трогает: распаковка — отдельный шаг
(`scripts/unpack-vendor.ps1`), а скрипты сборки работают по фиксированным
путям (`msvc-env.bat` L35-40, `mingw-env.sh`). Машинная карта раскладки —
`scripts/vendor-layout.json` (её исполняет unpacker); таблица ниже —
человеческий взгляд на тот же факт. Поэтому карта обязана давать и целевые
каталоги:

| архив `vendor/` | куда раскладывается |
|---|---|
| `tcl9.0.4-src.tar.gz` | `build/<цепочка>/tcl9.0.4/` (включая `pkgs/*`) |
| `tk9.0.4-src.tar.gz` | `build/<цепочка>/tk9.0.4/` |
| `dyncall-0.9.tar.gz`, `twapi-5.2.0-src.zip`, `Img-2.1.2.tar.gz`, `rl_json-0.17.8.tar.gz`, `mpexpr-1.2-vc.tar.gz`, `tkdnd-2.9.5.tar.gz`, `tktreectrl-2.5.1.tar.gz`, `itk-main-4.2.7.tar.gz` | `build/<цепочка>/ext/<верхний каталог архива>` |
| `tcllib-2.0.tar.xz`, `tklib-0.9.tar.xz`, `iwidgets-4.1.1.tar.gz`, `Cawt-3.1.1-User.zip`, `TclReadLine.zip` | `build/common/<имя>` — одни на обе цепочки |

Промеренные фактические имена: `build/msvc/ext/` содержит
`dyncall-0.9`, `Img-2.1.2`, `itcl4.3.8`, `itk-4.2.7`, `mpexpr`,
`rl_json-0.17.8`, `tk9.0.4`, `tkdnd-2.9.5`, `tktreectrl-2.5.1`,
`twapi-5.2.0`; `build/common/` — `cawt-3.1.1`, `iwidgets-4.1.1`,
`tcllib-2.0`, `TclReadLine`, `tklib-0.9`. Верхние каталоги архивов не всегда
совпадают с этими именами (например, `tkdnd-tkdnd-release-test-v2.9.5/` и
`itk-main/`), поэтому при раскладке имя переименовывается.

`itcl4.3.8` и `tk9.0.4` в `build/msvc/ext/` — **не копии, а джанкшены** на
`tcl9.0.4\pkgs\itcl4.3.8` и `tk9.0.4` соответственно; их создаёт шаг
сборки (`build-msvc-ext2.bat` L6-8) исключительно ради поиска
`nmakehlp -L` у itk. Своего исходного архива у itcl нет: он приходит внутри
тарбола Tcl. В MinGW-дереве таких джанкшенов нет — там itcl собирается
внутри core.

## Живая сверка карты

Каждая строка проверена не по локальной копии, а повторной загрузкой с
апстрима и сверкой четырёх вещей: размер → SHA-256 → читаемость байт как
архива → ожидаемый верхний каталог. Штатный инструмент —
`scripts/fetch-vendor.ps1`; промеры 2026-10-28 на этой машине:

```
fetch-vendor.ps1 -VerifyOnly          verdict: ok 15  bad 0  missing 0
fetch-vendor.ps1 -Force               15 архивов заново, 15/15 сверены,
                                      идемпотентно, 0 остаточных .part
fetch-vendor.ps1 -UsePins -VerifyOnly ok 11  bad 4
```

Третья строка — не ошибка, а ожидаемое поведение: `-UsePins` требует
пин-форму там, где в `vendor/` лежит веточная, и печатает оба размера в
каждой из четырёх строк (расхождение +1103 / +180 / +193 / +340 байта при
идентичном содержимом). Именно поэтому пины существуют.

Формулировка, которую можно считать гарантией этой карты: **для каждого из 15
сторонних компонентов канонический артефакт апстрима загружен и сверен
байт-в-байт (SHA-256 + размер) с тем архивом, из которого фактически
собирается winkit.** Исключений нет.

Плюс полный пофайловый разбор (не выборка из 2-3 файлов) нашего стейджа
против распакованного апстрима, для каждого компонента — таблица ниже и есть
его итог, а воспроизводится он так: распаковать архив из `vendor/`, пройти по
относительным путям и сравнить SHA-256 каждого файла, разделив расхождения на
«изменён у нас» (значит есть строка в `patches/README.md`) и «есть только у
нас / только у апстрима» (значит это артефакт сборки или наш prune):

| компонент | байт-в-байт | REAL-DIFF | чем объясняются расхождения |
|---|---|---|---|
| Tcl 9.0.4 | 2460 | 0 | 1411 «только у нас» — артефакты сборки; 1 «только в апстриме» — `pkgs/itcl4.3.8/tests/tclIndex` (наш prune) |
| Tk 9.0.4 | 955 | 0 | 1254 «только у нас» — артефакты сборки |

| dyncall 0.9 | 646 | 0 | 18 «только у нас» — 17 артефактов сборки + генерируемый `ConfigVars` |

`rename_file` без поля `file`, это `win/rules.vc` → `rules.vc.own`).
Единственное исключение лежит вне вендорного исходника и промерено здесь же:

**TWAPI `dyncall/dyncall-0.9/lib/release_amd64/*.lib`.** Три бинарных
предсобранных апстримных библиотеки (MSVC, `/MD`) заменяются нашими
пересобранными со статической CRT: `build-msvc-ext.bat` L17-20 и
`build-mingw-ext.sh` L19-22. Замер 2026-10-27:

| файл | апстрим | msvc (наш) | mingw (наш) |
|---|---|---|---|
| `libdyncall_s.lib` | 23 406 | 27 984 | 22 404 |
| `libdyncallback_s.lib` | 7 988 | 7 646 | 8 378 |
| `libdynload_s.lib` | 3 304 | 3 534 | 3 446 |

`release_x86/*.lib` при этом **не** трогается и остаётся байт-в-байт
апстримным (27 658 / 11 642 / 3 012) — мы собираем только x64. Ни `.lib` из
дерева twapi в образ не попадают (промер: в `build/msvc/kit/stage/` ноль
файлов `*.lib`), линкуется только наш пересобранный dyncall, поэтому
расхождение бинарников не влияет ни на один отгружаемый ассет.

Второе из этих двух в индексе `patches/README.md` **не значится**, хотя
`THIRD-PARTY-NOTICES.md` (раздел «Modifications and pruning») обещает, что
там записано всякое изменение вендорских исходников. Замена бинарной
библиотеки, которую выполняет сам сборочный скрипт, — изменение, и оно
задокументировано только в `docs/PLAN.md` L51 и в комментарии к
`build-msvc-ext.bat`. Это разрыв обещания с индексом, а не с лицензией:
dyncall распространяется по ISC-подобной лицензии (§ 3.3), которая требует
сохранить текст авторства, — он сохранён в
[`LICENSES/dyncall/LICENSE`](../LICENSES/dyncall/LICENSE). Строку в индекс
добавить нужно; делается это в том же коммите, что и остальной C/D-блок.

## Что из этого следует для воспроизводимости

* Все 15 файлов в `vendor/` сверены по SHA-256 **независимым пересчётом**
  (15/15 совпали с заявленными), и все 15 читаются как архивы с ожидаемым
  верхним каталогом — то есть ни один не является HTML-страницей с кодом 200.
* Все 15 URL проверены **повторной загрузкой с апстрима**, а не только
  локальной копией: `scripts/fetch-vendor.ps1 -VerifyOnly` даёт
  `ok 15 bad 0 missing 0`, а `-Force` перегружает все 15 заново с той же
  сверкой (промеры 2026-10-28, см. выше). itk, последний из незакрывавшихся,
  подтверждён пинком `e697407849b01d3498b56fc46e5a423690190954`.
* Четыре URL подвижны (ветка/`master` вместо тега или коммита); для них
  существуют настоящие пины коммитом, и их дигесты приведены отдельно, потому
  что они **не** совпадают с дигестами веточной формы при идентичном
  содержимом (+1103 / +180 / +193 / +340 байта).
* `vendor/` в репозиторий не входит, поэтому эта карта и есть интерфейс
  между «публичный репозиторий» и «собирается». Её цена — обязательность
  сверки до компиляции: неправильный архив, попавший в дерево, обнаружится
  не как ошибка загрузки, а как непонятный отказ `configure` вдалеке от
  причины (ровно этот класс мы уже ловили с `MSYSTEM`).

Загрузка и сверка автоматизированы (`scripts/fetch-vendor.ps1`, задача E5,
прогнана тремя способами: `-VerifyOnly` → 15/15 exit 0; `-UsePins -VerifyOnly`
→ `ok 11 bad 4` exit 1 с обоими размерами в каждой строке — ровно так и должно
быть, пока в `vendor/` лежит веточная форма; `-Force` → 15 архивов заново,
идемпотентно, 0 остаточных `.part`). До неё единственным источником истины
оставалась эта таблица.

Отдельный класс «воспроизводимости», который карта не покрывает: состояние
самой машины-сборщика просачивалось в **отгруженные бинарники** через
`*_VERSION_UUID` у `rl_json` и `itk` (оба берут `git rev-parse HEAD` внутри
дерева вендора, а оно лежит внутри нашего чекаута). Это провенанс-дефект, а не
дефект источника: тарбол был правильный, неправильным было то, что сборка из
него извлекала идентификатор git-репозитория окружения. Разбор и механизм
исправления — [`patches/README.md`](../patches/README.md) («UUID вендора в
собранных образах»); следующий по теме — раздел «PE `TimeDateStamp`» в
[`ENVIRONMENT.md`](ENVIRONMENT.md).
