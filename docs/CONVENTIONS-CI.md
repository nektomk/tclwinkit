# Кодировки и переводы строк — механика гейтов и CI

Действующие правила — в [`CONVENTIONS.md`](CONVENTIONS.md); история дефектов и
принятых решений — в [`CONVENTIONS-HISTORY.md`](CONVENTIONS-HISTORY.md). Здесь —
только механика: как именно проверяется, какие формы разбора обязательны, какие
числа добываются и что гейтами **не** покрыто.

CI разбит на два workflow (тот же коммит, что ввёл манифестный путь-фильтр):
`.github/workflows/encoding.yml` — дешёвые гейты на **каждый** пуш;
`.github/workflows/sources.yml` — перекачка/распаковка/патчи, только когда
затронут вход (скрипты fetch/unpack/apply/make-patches, `vendor-layout.json`,
`patches/**`, `vendor/manifest.json` или `.gitattributes`). `docs/SOURCES.md` —
не триггер: его строки живут в `fetch-vendor.ps1`, а паритет проверяет джоб
`encoding`. Так документарный пуш не перекачивает 15 архивов. Сами 15 архивов
кэшируются между прогонами (`actions/cache`, ключ — байты `scripts/fetch-vendor.ps1`
+ `vendor/manifest.json`): при бампе манифеста перекачивается только изменённый
компонент, а остальные 14 достаются из кэша; `fetch-vendor.ps1` при каждом
прогоне сверяет размер/SHA-256/форму каждой записи, кэшированной или нет, так
что устаревшая запись не протащит плохой архив в деревья.

## 1. Четыре гейта и их негативный контроль

| гейт | что проверяет | где живёт | в CI? |
|---|---|---|---|
| `scripts/check-encoding.ps1` | семь секций (ниже) | `scripts/` | джоб `encoding` |
| `scripts/verify-docs-artifact.ps1` | docs-архив | `scripts/` | локально (нет архива на чекауте) |
| `scripts/link-audit.ps1` | все ссылки и фрагменты `#…` трекингового markdown | `scripts/` | джоб `encoding` |
| `scripts/source-parity.ps1` | паритет `docs/SOURCES.md` и манифеста `scripts/fetch-vendor.ps1` | `scripts/` | джоб `encoding` |

Негативный контроль у всех четырёх — `scripts/check-gates-selftest.ps1`: строит
фикстуры с ровно одним внедрённым дефектом каждая и требует, чтобы гейт падал и
назвал именно этот дефект. Промер 2026-10-30: 126 утверждений (124 на голом
чекауте: два требуют собранных артефактов), 0 провалов, 34 класса дефектов и 6
охран «нога действительно прошла». Он же — первый шаг джоба `encoding`: этот
джоб — единственное место, где секции 4–6 не видят артефактов, а значит
единственное место, где молчаливый пропуск остался бы незамеченным.

Проверка времени: чередование old/new для фикстур показало 63,3 / 63,3 с и
60,5 / 60,1 с при +10 утверждений, то есть блок не стоит ничего. Первые два
прогона фикстур — 390,2 и 391,1 с — выглядели как шестикратная деградация гейта;
разложение по парам old/new показало, что это состояние машины (на диске лежали
140 МБ только что пересобранных `.exe`), а не цена фикстур.

## 2. Секции `check-encoding.ps1`

Номера в списке — ровно те, что гейт печатает в заголовках секций, чтобы вывод
сверялся с документом. Секции 4–6 требуют собранных артефактов: на свежем клоне
их нет, и там они **прыгают вслух** (`skip …` строкой в выводе), а не молча;
`-RequireArtifacts` превращает каждый пропуск в отказ. Причина ровно та же,
из-за которой появились все находки про молчаливый успех: гейт, который не
увидел проверяемого, неотличим от гейта, который его увидел.

```powershell
# 1. git ls-files --eol: индекс и рабочая копия
#    i/lf везде, w/lf кроме .bat/.ps1, attr/ сверен с .gitattributes

# 2. worktree bytes: ни BOM, ни лишнего CR — побайтово по ВСЕМ отслеживаемым
#    и подготовленным файлам (CR ожидается только у .bat/.ps1)

# 3. ни одного не-ASCII байта в .ps1, .bat и .sh
#    (побайтово, не через GetString: кодировка чтения здесь и есть предмет)

# 3b. каждый .ps1 обязан разбираться парсером PowerShell
#    (байты сами по себе не делают скрипт запускаемым, а джобов сборки в CI
#     нет, поэтому сломанный синтаксис иначе доехал бы до main незамеченным;
#     у Parser::ParseFile первый [ref] — ТОКЕНЫ, а не ошибки)

# 4. SHA256SUMS.txt: структура списка (ни пустой строки, ни CRLF, ни BOM) и
#    сверка множества дигестов с собранными exe; сам `sha256sum -c --strict`
#    в гейт не вызывается — он промерялся вручную (блок E), а гейт держит
#    ровно те свойства формата, которые его ломают

# 5. PE TimeDateStamp всех четырёх exe: не wall-clock (пришёл из блока E)

# 6. состояние сборки внутри образов: ни HEAD-хэша, ни вообще git-<sha>
```

## 3. Формы разбора, обязательные к применению

### 3.1 `git ls-files --eol` — регулярка, а не `Split("`t")`

Форму строки разбирать регуляркой: поля `i/…`, `w/…`, `attr/…` разделены
**пробелами**, таб стоит только перед путём. Наивный разбор по табам даёт ровно
одно поле и три пустых, и тогда проверка сообщает «все файлы нарушают» на
полностью чистом дереве — то есть её собственный отказ неотличим от отказа
проверяемого. Проверенная форма:

```powershell
if ($row -match '^(i/\S+)\s+(w/\S+)\s+(attr/\S.*?)\t(.+)$') { … }
```

и отдельный счётчик нераспарсенных строк: ноль нераспарсенных — часть
утверждения, иначе молчаливое «всё хорошо» на чужом формате вывода.

### 3.2 Сравнение времени ZIP — по UTC

`ZipArchiveEntry.LastWriteTime` для закреплённой записи отдаёт
`1980-01-01T00:00:00+03:00` на машине UTC+3: DOS-поле — это голый календарь без
зоны, и .NET помечает его offset'ом читателя. Проверка
`.LastWriteTime.UtcDateTime -eq 1980-01-01T00:00:00Z` отвергает **все 3129**
корректных записей (промер 2026-10-28). Сравнивать надо `.LocalDateTime` — это
и есть сырое значение поля, не зависящее от машины. Тот же номер проверяется на
каталожных записях отдельно: первая версия промера смотрела только файлы и
пропустила 504-байтный дрифт по 252 каталогам.

### 3.3 Записи docs-архива

Записи docs-архива (1980-01-01 по сырому полю, каталожные включительно),
кросс-сверку `MANIFEST.txt` с самим архивом, байтовую идентичность `LICENSES/` и
штамп `VERSIONS.txt` с датой коммиттера названного в нём коммита проверяет
`verify-docs-artifact.ps1` — локально, потому что архив живёт в `dist/`.

## 4. Числа не зашивать

Число файлов в проверку **не зашивается**: отслеживаемый набор растёт с каждым
блоком, и устаревшая константа превращает проверку в ложь (так было с «123
tracked files» в `.gitattributes` и с «131 файл» в этом документе — оба числа
устарели в том же блоке, что их записал). Считать надо самим `git ls-files`, а
утверждать форму, а не количество. Если где-то в конвенции написано число —
это снятое с промеренного состояния, и оно переписывается при каждом таком
промере.

## 5. `LICENSES/` и `make-licenses.ps1 -Check`

`LICENSES/` генерируется из вендорских деревьев, а вендорские тексты приходят с
CRLF (`Img/license.terms` — 41 пара, `libjpeg/README` — 374). Раньше
`make-licenses.ps1` копировал их `Copy-Item` побайтово, и эти два файла навсегда
оставались «изменёнными» в `git status` — что ломает и любой затвор на чистоту
дерева, и штамп `dirty working tree` в `VERSIONS.txt`. Теперь нормализация
CRLF→LF делается на байтовом уровне при генерации (не декодированием: часть
вендорских текстов не является валидным UTF-8, и round-trip испортил бы
лицензионный текст), а факт нормализации сообщается. Существующие затворы,
которые это правило уже покрывают косвенно:
`scripts/make-licenses.ps1 -Check` (`CHECK OK: LICENSES/ matches vendor sources`)
и `tests/kit-license-check.tcl` про обязательные тексты в образе.

## 6. Что гейтами **не** покрыто

* **Числовые противоречия** между документами — отдельный класс, не покрыт
  ни одним гейтом (детали и как снимались — в
  [`CONVENTIONS-HISTORY.md`](CONVENTIONS-HISTORY.md)).
* **Регистронезависимость имён переменных** в трёх сборочных скриптах — мина,
  на сегодня безопасная, отложено до пересборки (см. HISTORY).
* **Валидатор workflow-файла** лежит вне `scripts/` (`build/research/`, требует
  PyYAML); пока `.yml` проверяется им до коммита и самим GitHub при пуше.
